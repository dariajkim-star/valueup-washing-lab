# Story 6.4: 순위 불가의 사유 분리 (FR15) — 미공시 / 비가독 / 예고 / 무언급

Status: review

## Story

As a 애널리스트,
I want 순위에서 빠진 종목이 **회사가 안 낸 것**인지 **우리가 못 읽은 것**인지 구분해 보는 것,
so that 전자는 판단 재료로 쓰고 후자는 우리 백로그로 보낸다.

## Acceptance Criteria (epics.md 6.4 / PRD FR-15)

1. 순위 불가 종목이 **미공시 / 비가독 / 무언급** 셋 중 하나로 판정되고, 근거가 함께 노출된다.
2. **미공시는 신호다** — 조용히 빠지지 않고 화면에서 *"회사가 목표를 제시하지 않음"*으로 드러난다.
3. **비가독은 우리 한계다** — 계속 벌점 없이 제외되고 첨부 취득 워크리스트로 간다.
4. **무언급은 판정 보류다** — 근거 없이 미공시로 세지 않는다(NFR2).
5. 판정은 **단일 정의처**를 통한다(`declares_no_attachment`와 나란히).
6. `execution_score`·`opacity_rank` **수치는 바뀌지 않는다** — 순위·문구·워크리스트만.

## ⚠️ 착수 전에 읽어라 — 이 스토리가 위험한 이유

**이 스토리는 2026-07-28에 폐기한 규칙과 같은 모양의 규칙을 다시 만든다.**

그때 `is_unrankable`은 *"첨부 참조 문구 AND count==4"*였고, 실 DB 첫 적재에서 **참조 검사의
변별력이 0**임이 드러나 참조 검사를 **버렸다**. 이유는 하나였다 — `관련 웹페이지`가 DART
표준 서식 필드라 26/26 전건에 있었고, 규칙은 6종목을 내용이 아니라 **정규식 운**으로 갈랐다.
불투명순 정렬의 **1·2·3등이 전부 오탐**이었다.

이번에 다시 만드는 것은 **같은 재료(참조 문구)를 쓰지만 다른 자리에 놓는다**:

| | 2026-07-28 (폐기) | 2026-08-07 (이 스토리) |
|---|---|---|
| 쓰임 | **순위 대상 여부**를 가르는 게이트 | 이미 빠진 것의 **사유 라벨** |
| 틀렸을 때 | 오탐이 1·2·3등으로 올라온다 | 라벨 하나가 틀린다(순위 불변) |
| 실패 비용 | 화면의 최상단 | 배지 문구 |

**게이트가 아니라 라벨이다.** 그래서 되살리는 것이 아니다 — 그러나 **변별력 검증은 그때와
똑같이 해야 한다.** 아래 §실측이 그것이다.

> NFR2: **애매하면 null.** 근거가 없으면 미공시로 세지 않고 **무언급**에 둔다.
> "회사가 공시하지 않았다"와 "우리가 읽지 못했다"는 다른 범주이고,
> **"둘 중 어느 쪽인지 모른다"도 세 번째 범주**다. 두 개로 접으면 그것이 세탁이다.

### 층이 틀려서 순환 임포트가 났다 (설계 정정)

`unrankable_reason`을 `opacity_engine`에 뒀더니 서빙(`screening`·`valueup_score`)에서
부르는 순간 **순환 임포트**가 났다 — `opacity_engine`은 repository를 임포트하는 **배선 층**이다.
이 방의 원칙(*반증 재료가 사는 곳이 게이트의 층을 정한다*)을 층 자체에 적용해 정리했다:

```
plan_selection.py   축 정의 + 그 파생(opacity_count · is_unrankable)   ← 의존성 0
plan_signals.py     판정 어휘(declares_no_attachment · references_external_plan)
                    + unrankable_reason · plan_reason_row              ← plan_selection만 의존
opacity_engine.py   DB 배선. 위 이름들을 **재수출**해 기존 호출부·테스트를 그대로 둔다
```

`opacity_count`·`is_unrankable`을 `plan_selection`으로 옮긴 것은 취향이 아니라 층이다 —
축 정의(`OPACITY_AXES`)가 거기 있으므로 그 파생도 거기가 제자리다.

## 범위 확장 — OQ-4 종결로 **네 번째 범주** (2026-08-07 오후)

셋으로 가른 직후 Boundary가 물었다: *"OQ-4의 예고 56건은 그 셋 중 어디에 있어?"*
답은 **무언급 안**이었고, 세어보니 **67건 중 56건**이었다. **"판정 보류"라던 통의 84%가
실은 애매하지 않았다 — 우리가 제목을 안 봤을 뿐이다.**

```
축=0 구간 206건       셋으로 갈랐을 때        넷으로 가른 뒤
  미공시                     110      →           110
  비가독                      29      →            29
  예고                         –      →            56
  무언급                      67      →            11   ← 진짜 모르는 것
```

### 여기서도 변별력 함정이 있었다 (하루에 두 번째)

```
`예고(안내공시)` 문자열 보유       104건
  제목 서식 `…예고(안내공시)/(`     56건  ← 이 문서가 예고다
  ※관련공시 목록 안                48건  ← 진짜 계획이 자기 예고를 나열
```

단순 포함으로 잡으면 **`axis_targets` 40건이 예고로 뒤집힌다** — 목표를 다 공시한 회사가
"예고만 한 회사"가 되는 것이다. DART 제목줄이 `회사명/보고서명/(YYYY.MM.DD)` 서식이라
뒤따르는 `/(`가 제목임을 증명한다. `게재`·`관련 웹페이지`와 **같은 계열**이고, 오늘
오전에 한 번 걸릴 뻔했던 함정을 오후에 또 만났다.

### 배선이 조용히 무력했다 (실측이 잡음)

워크리스트에 `is_notice(chosen.get("raw_text"))` 가드를 넣었는데 **19건 그대로**였다.
`build_worklist`가 만드는 row dict에 `raw_text`가 없어서 **항상 `is_notice(None)` = False**였다 —
가드가 존재하지만 아무것도 막지 않는 상태. `attachment_absent`와 같은 방식으로 row 생성
시점에 `is_notice`를 계산해 넣어 고쳤다.

> **이 방이 반복해서 맞는 결함이다** — 판정은 맞는데 배선이 안 됨(`exempt_short_form`
> 102건이 화면에서 침묵했던 것과 같은 계열). 잡은 것은 코드 리뷰가 아니라 **숫자가
> 안 움직였다는 사실**이었다. 변동 0을 보고하는 규율이 여기서 값을 했다.
